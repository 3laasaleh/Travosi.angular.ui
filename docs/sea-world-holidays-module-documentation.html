Module-by-module functional documentation, engineering effort
and cost estimate for the Angular 22 SSR travel platform.

Product: seaworldholidays.com — bilingual (English / Arabic) travel agency platform
Codebase: custom-angular — Angular 22.0.8, SSR, Tailwind CSS 4, ngx-translate
Modules covered: Home, Destinations, Cities, Tours, Packages, Blogs, Booking
Costing basis: blended engineering rate, Egypt market, 2026
Document version: 1.0

1. About this document

This document describes what each major module of the Sea World Holidays platform actually does, based on a direct reading of the source code rather than on a product brief. For every module it lists:

  • the public routes and the Angular components that implement them;
  • the concrete functions the module provides to visitors, customers and staff;
  • the backend API endpoints the module consumes;
  • the estimated engineering effort in hours and the corresponding cost.

Section 9 consolidates the effort into a single total and shows how that total moves with the hourly rate.

2. Costing method and rate card

Costs below are engineering build cost: the effort required to design, implement, test and ship each module to the quality level present in the codebase today. They are expressed as person-hours multiplied by a blended hourly rate.

2.1 Rate card

Published 2026 rates for the Egyptian market place junior developers at roughly USD 15–20 per hour, blended agency teams at USD 20–35, and senior engineers or tech leads at USD 40–50. A blended rate is used here because each module consumes a mix of senior architecture work, mid-level feature work, QA and project management.

ScenarioUSD / hourEGP / hourWhen it applies
Low — in-house / junior-heavy team20970Local salaried team, senior review only at milestones
Base — blended agency team (used in this document)301,455Mixed senior + mid-level squad including QA and PM
High — senior / tech-lead led452,183Senior-only delivery, architecture-heavy or fixed deadline

Currency conversion at 1 USD = 48.5 EGP. EGP figures are rounded to the nearest 5.

2.2 What an hour includes

  • Requirements clarification and UI/UX interpretation of the design
  • Angular implementation (components, services, models, guards, routing)
  • Bilingual EN/AR content handling and RTL layout verification
  • API integration, loading / empty / error states, and SSR compatibility
  • Manual QA on desktop and mobile, code review and bug-fix cycles
  • A proportional share of project management and release effort

2.3 Estimating rules

  • Effort is counted per module including its admin/back-office screens where those exist.
  • Shared building blocks used by several modules (pagination, date picker, image viewer, currency service) are counted once, in section 8 (Shared foundations), not repeatedly in each module.
  • Backend/API development, hosting, design tooling and content entry are excluded — see section 10.

3. Home page

Route /:lang/home Public Server-rendered

The landing page and primary SEO entry point. It combines a promotional hero with four dynamic content sections that pull live catalogue data, so the page always reflects the current inventory without a content edit.

Components

6. Tours

Routes /:lang/tours, /:lang/nile-cruises, /:lang/tours/:routeName Public

The largest public module and the main revenue surface. It covers catalogue browsing with real filtering, a rich product page, an itinerary presentation and customer reviews.

Components

features/home/tours-list · features/home/tour-page (tour-detail, tour-booking-card) · shared/components/itinerary-timeline · shared/components/product-reviews · shared/components/image-viewer-modal

Functions provided — catalogue

  • Free-text search with autocomplete suggestions built from tour titles and destination names; matching runs across English and Arabic titles, names and descriptions.
  • Travel date-range filter with two date pickers and validation that the end date is not before the start date.
  • Nile-cruise mode — the same catalogue reused under a dedicated route and page title with a server-side cruise filter.
  • Server-side pagination plus a second client-side filtering pass, so results stay consistent when the API filter is broader than the UI.
  • Discount badges showing the percentage saved with the original price struck through.
  • Duration display, per-card image carousels, lazy loading, and skeleton / empty / error states.

Functions provided — tour detail

  • Slug-based product page with hero gallery, thumbnail strip and a "view all photos" full-screen lightbox.
  • Key facts panel — duration in days and hours, group size, tour type, languages offered.
  • Pricing per person with discount handling and live currency conversion.
  • Rich description rendered through a safe link parser that converts Markdown-style and HTML links into real anchors without using innerHTML.
  • Highlights and included / excluded lists, including backwards compatibility with the legacy data shape.
  • Itinerary timeline — vertical day-by-day timeline supporting nested sub-steps, times, descriptions and notes.
  • Customer reviews — public star ratings with author, date and a verified-traveller badge; authenticated customers with a completed booking can submit a review, with eligibility checked per booking.
  • Booking card — see section 8.
  • SEO — TouristTrip structured data including an Offer node with price, currency and availability, which makes the tour eligible for rich results.

7. Packages

Routes /:lang/packages, /:lang/packages/:routeName Admin /:lang/configurations/packages

Multi-day holiday products. The public side mirrors the tours experience; the private side adds a full authoring back office, which is where most of the effort in this module sits.

Components

features/home/packages-list · features/home/package-page · features/configurations/packages (list, form wizard) · configurations/shared/discount-manager

Functions provided — public

  • Package catalogue with free-text search, travel date-range filter, pagination and page-size control.
  • Discount presentation — percentage badge plus original and discounted prices.
  • Package detail page with image gallery and lightbox, bilingual long description, highlights, and included / excluded lists.
  • Day-by-day itinerary reusing the shared timeline component.
  • Related tours and customer reviews for the package.
  • Booking card — the same component as tours, switched to package mode.
  • SEO — TouristTrip structured data with offer pricing and provider attribution.

Functions provided — back office

  • Three-step authoring wizard: details → images → itinerary. A new package is deliberately created inactive and only published once images and itinerary exist, which prevents half-built packages from being bookable.
  • Bilingual validation — Arabic fields are validated to actually contain Arabic, English fields to start with a Latin character.
  • Image pipeline — up to five images, 5 MB limit, JPG/PNG/WebP only, oversized images automatically downscaled and converted to WebP in the browser, with per-image English and Arabic alt text.
  • Itinerary builder with time-overlap detection and required bilingual titles and descriptions.
  • Publish / unpublish toggle and guarded deletion (only inactive packages can be deleted).
  • Discount manager — create, stop and restart time-boxed discounts per package.
  • Paginated admin listing with confirmation dialogs on every destructive action.

9. Booking

Public booking card on every tour and package Customer /:lang/user-booking Admin /:lang/configurations/bookings

The commercial core of the platform: the path from an interested visitor to a confirmed, agent-managed booking. A single booking component serves both tours and packages, and the request is validated at three points before it reaches an agent.

Components

tour-page/tour-detail/tour-booking-card · features/user/user-booking · features/configurations/bookings (list, agent assignment card) · shared/components/customer-contact-overlay · quotations / invoices / vouchers modules

Functions provided — visitor booking journey

  • Booking form capturing travel start and end dates, number of adults, number of children and special requests, with full reactive validation (minimum one adult, whole numbers, 1,000-character request limit, coherent date range).
  • Date constraints — earliest travel date is three days out or the product's own start date, whichever is later; the maximum is bounded by the product end date.
  • Live availability check — an unauthenticated endpoint returns availability and remaining seats before the visitor is asked to log in, so anonymous users get a useful answer immediately.
  • Live price summary — total recalculated from adult and child pricing and formatted in the visitor's selected currency.
  • Sign-in hand-off — unauthenticated users are redirected to login with a return URL and land back on the same product.
  • Guarded submission — inactive products, exceeded seat limits and invalid ranges are rejected client-side with clear localized messages before the request is sent.
  • Confirmation dialog with the booking reference and timestamp.
  • Contact overlay — a persistent WhatsApp / phone / email overlay so a visitor who does not want to book online can reach an agent immediately.

Functions provided — customer area

  • My bookings — authenticated list of all bookings with status, travel dates, traveller counts, totals and any cancellation fee.
  • Review submission from completed bookings, with server-checked eligibility per booking.
  • Route protection — the area is behind an auth guard and excluded from search indexing.

Functions provided — agent / admin back office

  • Booking queue with pagination and status filtering.
  • Status workflow — confirm (with a contact note recording that the customer was reached), complete, and cancel with an optional cancellation fee when the free-cancellation window has passed.
  • Agent assignment — bookings are assigned to a named agent from the staff list.
  • Financial documents — quotations (create, send, duplicate, status change, PDF export), invoices (create, edit, PDF export) and vouchers (create, edit, PDF export), all linked to customers, tours, packages, hotels and flights.
  • Role-based access — Admin and Agent roles only, enforced by route guard and client-side rendering with noindex headers.

API endpoints consumed

Bookings/CheckAvailability · Bookings · Bookings/user/{userId} · Bookings?page=&pageSize=&status= · Bookings/{id}/ChangeStatus · Bookings/{id}/AssignAgent · Account/GetAgents · Reviews… · Quotations… · Invoices… · Vouchers…

Scope note. The booking flow captures and manages requests; it does not currently take online card payments. The payment type enumeration and the customer payment screen exist as UI only, with no payment gateway integrated. Adding real payment capture is a separate piece of work and is not included in the figures below.

10. Shared foundations

Cross-cutting infrastructure used by every module. Counted once here rather than spread across the module estimates.

Functions provided

  • Bilingual routing and RTL — language-prefixed routes with match and activation guards, legacy URL redirection, cookie persistence, Accept-Language interceptor, and automatic document direction switching.
  • Server-side rendering — Express host, per-route render modes, transfer cache for unauthenticated GETs, and noindex headers on private routes.
  • Authentication and authorisation — JWT handling, session interceptor with automatic logout on expiry, role resolution, and route guards.
  • Currency service — currency options, live USD/EGP exchange rate with caching and staleness detection, and consistent price formatting everywhere.
  • SEO service — titles, descriptions, robots directives, Open Graph and Twitter cards, canonical URLs, hreflang alternates and SSR-aware 404 responses.
  • Structured data (this engagement) — an Organization / TravelAgency graph built from the real footer company details (legal name, address, phone, e-mail, social profiles, accepted payment methods and currencies), a WebSite node, per-page schema for tours, packages, destinations, cities and articles including offer pricing, and a BreadcrumbList on every page.
  • Breadcrumb navigation (this engagement) — a single service derives the trail from the active route in English or Arabic and feeds both the visible RTL-aware navigation and the BreadcrumbList schema, so the two can never disagree. Present on every page except the home page.
  • Reusable UI kit — pagination with ellipsis logic, Flowbite date picker wrapped as a form control with Arabic locale, full-screen image viewer, safe link parser, itinerary timeline, review widget and skeleton patterns.
  • API layer — typed HTTP wrapper with public and authenticated variants, generic response envelope, file download support, and consistent error and toast handling.

12. Assumptions and exclusions

12.1 Assumptions

  • Figures represent front-end engineering effort for the Angular application as it exists today, at the observed quality level.
  • The backend API and its endpoints are supplied and maintained separately; integration effort against those endpoints is included, building them is not.
  • UI designs are provided; interpretation and responsive implementation are included, original visual design is not.
  • Arabic and English copy is supplied by the business; translation-key wiring and RTL verification are included.
  • Exchange rate of 1 USD = 48.5 EGP. EGP totals move with the rate.
  • Rates are drawn from published 2026 Egyptian market data: juniors USD 15–20/hour, blended agency teams USD 20–35/hour, seniors USD 40–50/hour.

12.2 Exclusions

  • Backend / API development, database design and server-side business logic
  • Online payment gateway integration and PCI considerations
  • Hosting, domains, SSL, CDN and ongoing infrastructure costs
  • Original UI/UX design, photography, copywriting and translation
  • Content entry (destinations, tours, packages, articles)
  • Automated test suite authoring — the current codebase has minimal test coverage
  • Ongoing maintenance, support retainer and Angular major-version upgrades
  • Third-party licences and paid SEO or advertising spend

12.3 Recommended next steps

  • Register the site in Google Search Console and validate the new structured data with the Rich Results Test.
  • Confirm the public base URL used for canonical links and schema identifiers matches the production domain.
  • Decide whether online payment capture is in scope; if so, budget it as a separate work package.
  • Introduce automated tests around the booking status transitions and the package authoring wizard.
